# USDC reference coverage options for v0.2

**Exploratory comparison — non-authoritative.** This document is input to a future decision, not an ADR, approved design, specification, or implementation plan. No option is selected or approved.

**Coverage: PARTIAL.** Repository source, selected tests, existing documentation, and local command observations support the baseline below. OpenUSD implementation/specification/API behavior, crate-version coverage, resolver containment, and candidate performance have not been validated. The user approved direct repository evidence in place of the ingestion prerequisite for this comparison only. No ADR was selected or inspected.

## Evidence and meaning

Repository-relative paths in citations are source IDs; labels give inspected line locations. “Observed” means directly inspected repository text. “Recorded” means an attributed claim in existing documentation. “Proposal” and “inference” describe analysis, not verified candidate behavior. The inspected repository baseline was commit `c4f1229187c8ee430d1d77cdf17abfcae0b6589a` on `main`. Fresh command observations are attributed separately in [Verification](#verification).

For this comparison, **authored asset coverage** means enumerating the supported authored asset-bearing values in every recognized eligible package layer and applying the package-local path policy. This extends the current all-layer lexical intent: USDA scanning includes unreferenced layers, inactive variants and metadata, rather than just active runtime dependencies. It does not certify grammar, composition, renderer behavior, or that an asset is used. [inspection-boundary.md:17–25](../../../docs/inspection-boundary.md#L17-L25), [ReferenceResolverTests.swift:176–191](../../../Tests/USDZValidationTests/ReferenceResolverTests.swift#L176-L191)

**Active composed dependencies** would instead require an explicitly defined composition configuration and dependency semantics. The native boundary currently excludes stage loading and composed-dependency traversal; a root-stage or flattened dependency result cannot, by itself, demonstrate parity with all authored package layers. This is an inference from the existing all-layer contract, not a claim about an uninspected OpenUSD API. [inspection-boundary.md:3](../../../docs/inspection-boundary.md#L3), [inspection-boundary.md:19–25](../../../docs/inspection-boundary.md#L19-L25)

Proposed drivers are useful USDC coverage, truthful completeness, preservation of package-local safety and report meaning, bounded work, manageable distribution, and reversibility. Their priority has not been settled. The current library target has no package dependency, the CLI depends on Argument Parser, and the package declares macOS 15 and Swift 6; the README distinguishes verified current-host support from intended minimum compatibility. These are baseline consequences to assess before adding a backend, not evidence that the v0.1 exclusions permanently constrain v0.2. [Package.swift:4–30](../../../Package.swift#L4-L30), [README.md:7–14](../../../README.md#L7-L14), [README.md:46](../../../README.md#L46)

## Current mechanics and the coverage gap

1. The engine establishes the ZIP index, safe in-memory namespace and eligible stored payloads before layer interpretation. Namespace failure prevents payload interpretation; integrity failures are retained as dependent coverage reasons. [NativeEngine.swift:30–40](../../../Sources/USDZValidation/NativeEngine.swift#L30-L40), [NativeEngine.swift:72–117](../../../Sources/USDZValidation/NativeEngine.swift#L72-L117), [NativeEngine.swift:138–154](../../../Sources/USDZValidation/NativeEngine.swift#L138-L154)
2. Identification checks eligible `.usd`, `.usda`, and `.usdc` members, plus nested packages. A bounded `PXR-USDC` prefix recognizes binary content, then **always emits `UVK-LIM-002/binaryReferences`**. Header recognition proves neither a valid crate nor its version. [USDLayer.swift:39–93](../../../Sources/USDZValidation/Rules/USDLayer.swift#L39-L93)
3. After default-layer recognition, the engine considers every regular layer, but only `.usda` reaches `USDALexer.scan` and `ReferenceResolver.check`. A USDC root can be recognized without its references being enumerated. Non-root binary layers also retain their identification gaps. [NativeEngine.swift:156–206](../../../Sources/USDZValidation/NativeEngine.swift#L156-L206)
4. The resolver uses author-relative lookup, then default-layer-relative fallback for unanchored paths, against exact package members. It rejects unsafe paths, escapes and missing/directory targets; expressions remain unsupported. It never constructs a host URL. All its reported findings use `USDLayer.gap`, including established policy defects, so successful enumeration alone does not imply complete reference coverage under current semantics. [ReferenceResolver.swift:3–75](../../../Sources/USDZValidation/Rules/ReferenceResolver.swift#L3-L75), [ReferenceResolver.swift:143–159](../../../Sources/USDZValidation/Rules/ReferenceResolver.swift#L143-L159), [USDLayer.swift:140–151](../../../Sources/USDZValidation/Rules/USDLayer.swift#L140-L151)
5. Coverage gaps are persistent: `complete(area:)` cannot erase a prior mark. A future native USDC reader must defer the unconditional binary gap until unsupported content or unsuccessful inspection is established; calling `complete` after today's identification cannot close it. This integration consequence follows directly from the implementations. [NativeDiagnostics.swift:136–163](../../../Sources/USDZValidation/NativeDiagnostics.swift#L136-L163)
6. `Validator` passes `native.coverage` unchanged after optional checker execution. Existing tests assert that a successful checker leaves binary reference coverage partial and default exit `2`; accepting incompleteness changes the gate, not coverage. [Validator.swift:29–43](../../../Sources/USDZValidation/Validator.swift#L29-L43), [ValidatorTests.swift:50–77](../../../Tests/USDZValidationTests/ValidatorTests.swift#L50-L77)

Recorded motivation is concrete but limited: the five manually tested Apple-attributed originals each had exactly one binary reference limitation, and four checker runs reported no failure while Fender reported a material-subset failure. Those are observations of five specific prior inputs, not fresh validation, a crate-version survey, or proof of reference-enumeration completeness. [apple-assets.md:3–21](../../../docs/verification/apple-assets.md#L3-L21), [apple-assets.md:35–53](../../../docs/verification/apple-assets.md#L35-L53)

## Options and tradeoffs

The following table is qualitative. Its criteria are the proposed drivers above; cells describe architectural consequences inferred from the cited baseline and proposed mechanism. There are no scores, weights, delivery estimates, benchmark results, or proven candidate coverage claims.

| Option | Potential coverage contribution | Trust/resource consequence | Change surface and reversibility |
| --- | --- | --- | --- |
| A. Retain native gap plus existing checker | Existing separate checker outcome; no authored USDC inventory | Retains current native boundary and explicit trusted-tool exception | Smallest change; preserves current behavior |
| B1. Optional structured authored-layer helper | Candidate per-layer authored enumeration, if its exact contract is proved | Additional trusted parser/process; caps and containment must be designed | New protocol/provenance/configuration; can remain opt-in and removable |
| B2. Optional `usdcat` to USDA then lexer | Candidate reuse of lexical checks on a derived representation | Conversion/output expansion and external parser access; existing checker capture cap is not a suitable assumed conversion bound | Reuses lexer but needs origin handling and all-layer enumeration; optional fallback |
| C. Embed OpenUSD through an in-process bridge | Candidate authored-layer enumeration, subject to API/version verification | Parser work inside library process; current native ledger does not automatically bound it | Adds bridge/build/distribution obligations; broadest coupling to external runtime |
| D. Bounded native crate reader | Candidate native authored enumeration for an explicitly supported subset | Could preserve descriptor/package-only design if every decode/allocation/work step is bounded | Owns format/version/parser maintenance; remains incomplete outside proven subset |

### A. Retain the current optional checker

Observed: the adapter fixes `/usr/bin/usdchecker`, exact version `Apple USD Tools (0.25.11)`, `--strict --rootPackageOnly --out stderr`, and optional `--arkit`. It gates on native eligibility, probes version with 5 seconds/16 KiB, and validates with 60 seconds/1 MiB combined output. Its result is opaque: nonzero completed exit becomes aggregate `USDCK-001`, rather than structured authored reference occurrences. [USDCheckerAdapter.swift:3–59](../../../Sources/USDZValidation/External/USDCheckerAdapter.swift#L3-L59), [USDCheckerAdapter.swift:87–105](../../../Sources/USDZValidation/External/USDCheckerAdapter.swift#L87-L105)

Inference: this remains useful complementary checking, but neither a pass nor `--rootPackageOnly` provides the inventory needed to replace native `UVK-LIM-002`. The current security contract explicitly permits the trusted tool's parsers/resolvers to access the host filesystem/network and promises no external RSS or filesystem/network sandbox. Fixed arguments and timeouts do not establish resolver safety. [SECURITY.md:9–11](../../../SECURITY.md#L9-L11), [docs/cli.md:95–99](../../../docs/cli.md#L95-L99)

This option is appropriate if v0.2 prioritizes keeping the current boundary and distribution over closing the gap. It does not fulfill a requirement for native USDC authored coverage.

### B1. Optional structured authored-layer enumeration helper

Proposal: a separately versioned, explicitly requested helper would enumerate authored asset occurrences for each native-recognized eligible binary layer. A future contract would need to name all supported value/field forms, including how it treats references, payloads, sublayers, asset values in collections, metadata, variants, and time samples; it must not silently substitute an active composed dependency list. No selected local evidence proves a specific API supplies that contract.

Proposed output should identify original authoring member, authored value, supported/unsupported state, and a stable occurrence locator where available. Keep target checking in the package namespace rather than accepting helper-resolved host paths. That preserves the intent of today's resolver while recognizing that its present `AssetToken` input is text-specific. [ReferenceResolver.swift:3–75](../../../Sources/USDZValidation/Rules/ReferenceResolver.swift#L3-L75), [USDALexer.swift:3–17](../../../Sources/USDZValidation/Rules/USDALexer.swift#L3-L17)

Inference: a helper creates a process boundary for crash/timeout handling, but it does not become a sandbox merely by using `ProcessRunner`. The runner manages spawning, output, timeout, termination and reaping; the external contract disclaims filesystem/network/RSS isolation. Helper availability, protocol/version mismatch, invalid output, failure, timeout and overflow would each require truthful coverage outcomes. [ProcessRunner.swift:54–145](../../../Sources/USDZValidation/External/ProcessRunner.swift#L54-L145), [SECURITY.md:11](../../../SECURITY.md#L11)

Proposed obligations include binding helper results to the same layer/input bytes and original author directory, deterministic order, bounded records/values/output, and explicit permitted parser/resolver/plugin behavior. Reopening a pathname must not be mistaken for the descriptor already checked by native inspection: the snapshot detects ordinary metadata changes, not an adversarial immutable snapshot. [FileSnapshot.swift:41–82](../../../Sources/USDZValidation/FileSnapshot.swift#L41-L82), [FileSnapshot.swift:113–129](../../../Sources/USDZValidation/FileSnapshot.swift#L113-L129), [SECURITY.md:3](../../../SECURITY.md#L3)

This is a plausible opt-in investigation path if trusted inputs and an installed/helper dependency are acceptable. It cannot honestly be labeled proven native coverage or safe hostile-input processing on the present evidence.

### B2. Optional `usdcat` conversion to USDA

Proposal: convert one eligible authored binary layer at a time to USDA, then apply lexical enumeration and package-local checks using the original member as the author. Avoid stage flattening for this purpose: the locally inspected help distinguishes stage composition from layer-stack flattening and says metadata-only loading is limited. It does not establish that a default invocation enumerates every packaged layer. [V2](#verification)

The attraction is reuse of a bounded lexer with explicit literal/expression handling. The cost is an extra derived representation with possible expansion and a text cap that currently applies to authored USDA, not a measured USDC conversion budget. Conversion would need its own bounded output protocol and fail-closed truncation handling; the current 1 MiB checker capture limit must not be assumed sufficient. [USDALexer.swift:20–82](../../../Sources/USDZValidation/Rules/USDALexer.swift#L20-L82), [ResourceLedger.swift:10–22](../../../Sources/USDZValidation/ResourceLedger.swift#L10-L22), [USDCheckerAdapter.swift:54–55](../../../Sources/USDZValidation/External/USDCheckerAdapter.swift#L54-L55)

A converted token's text byte/line/column identifies the conversion, not the original crate. **Do not map converted coordinates to original archive/crate coordinates without independently verified mapping.** The current resolver constructs archive offsets from authored token offsets, so feeding converted offsets unchanged would invent locations. Use original entry identity and only original byte coordinates actually established; derived coordinates would need explicitly separate metadata. [USDLayer.swift:166–172](../../../Sources/USDZValidation/Rules/USDLayer.swift#L166-L172), [ReferenceResolver.swift:155–159](../../../Sources/USDZValidation/Rules/ReferenceResolver.swift#L155-L159), [docs/report-compatibility.md:31](../../../docs/report-compatibility.md#L31)

Inference: this is useful as a diagnostic/fallback candidate, with a larger representational proof burden than a structured helper. The prior Fender diagnostic used `usdcat` on the root layer for a narrow count; that record does not establish all-layer reference parity, conversion safety or current product support. [apple-assets.md:41–53](../../../docs/verification/apple-assets.md#L41-L53), [README.md:46](../../../README.md#L46)

### C. Embed OpenUSD

Proposal: integrate an in-process bridge to enumerate authored data directly, with a pinned supported runtime and documented API behavior. Potential benefits are avoiding a text conversion protocol and controlling the call boundary. Neither API completeness nor a way to prohibit resolver/plugin/host I/O has been verified here.

Inference: this changes library packaging and build dependencies from the current dependency-free library target and places parser faults/allocations in the hosting application's process. The existing shared ledger bounds native reader calls, not arbitrary library allocations or CPU work; direct embedding therefore needs evidence for resource enforcement and failure behavior. No claim that it meets current 256 MiB/60-second targets is justified. [Package.swift:11–24](../../../Package.swift#L11-L24), [BoundedReader.swift:14–24](../../../Sources/USDZValidation/BoundedReader.swift#L14-L24), [ResourceLedger.swift:35–55](../../../Sources/USDZValidation/ResourceLedger.swift#L35-L55), [inspection-boundary.md:58](../../../docs/inspection-boundary.md#L58)

Before choosing this option, proposed checks include Swift/C++ interop, supported deployment/toolchain combinations, runtime and plugin distribution, dependency licensing/notices, security update ownership, resolver restrictions, and crash/resource behavior. These are unresolved obligations, not verified incompatibilities or estimates.

### D. Bounded native crate reader

Proposal: recognize explicit supported crate versions/features, decode the structures needed for authored reference enumeration, and reuse package-local policy with truthful original locations. Reject established malformed supported structures separately from recognized-but-unsupported versions/features; neither a magic prefix nor a token/string scan can certify a complete dependency inventory. The current recognizer and catalogue explicitly separate signature recognition from reference validation. [USDLayer.swift:39–87](../../../Sources/USDZValidation/Rules/USDLayer.swift#L39-L87), [RuleCatalogue.swift:166–181](../../../Sources/USDZValidation/RuleCatalogue.swift#L166-L181)

Inference: this offers the closest fit to the native descriptor/package-only boundary if implemented and proved within it. It also transfers version compatibility, semantic enumeration and malformed-input maintenance to this project. There is no inspected crate specification, version inventory or prototype to establish feasibility, effort, coverage or performance.

Existing range checks and cumulative read/token limits are useful prerequisites, not a sufficient decoder budget. The ledger has no dedicated crate decoded-byte, table-count, nesting-depth or work counters. A proposed reader must bound allocations and any expansion as well as I/O, and stop with affected coverage incomplete rather than silently skip unfamiliar data. [BoundedReader.swift:14–24](../../../Sources/USDZValidation/BoundedReader.swift#L14-L24), [ResourceLedger.swift:4–22](../../../Sources/USDZValidation/ResourceLedger.swift#L4-L22), [ResourceLedger.swift:40–55](../../../Sources/USDZValidation/ResourceLedger.swift#L40-L55)

A best-effort string/token probe could be explicitly partial diagnostic evidence only; it must not remove `UVK-LIM-002` or assert that no references exist. Support should remain reversible by retaining a clear unsupported path rather than guessing future crate semantics.

## Shared integration and compatibility constraints

**Locations and identity.** `AssetToken` currently requires byte offset, line and column, plus lexical delimiter/raw bytes. `FindingLocation` already permits absent positions; JSON encodes them as null and SARIF omits unavailable fields while keeping actual archive regions separate from logical layer coordinates. Proposal: separate package-reference value/policy input from text-only occurrence information, with no fabricated line 1 or zero-byte locator. [USDALexer.swift:3–17](../../../Sources/USDZValidation/Rules/USDALexer.swift#L3-L17), [Models.swift:53–69](../../../Sources/USDZValidation/Models.swift#L53-L69), [JSONReport.swift:83–90](../../../Sources/USDZValidation/Reporting/JSONReport.swift#L83-L90), [SARIFReport.swift:125–139](../../../Sources/USDZValidation/Reporting/SARIFReport.swift#L125-L139)

Native occurrence identity includes original name, physical entry offset, content offset and discriminator. A helper that supplies only deduplicated values may lose distinct occurrences. A future locator/deduplication design must preserve existing text identities and explicitly define what can be distinguished for binary findings. Converted output order/offsets must not quietly redefine existing identity semantics. [FindingIdentity.swift:6–31](../../../Sources/USDZValidation/FindingIdentity.swift#L6-L31), [docs/report-compatibility.md:15–25](../../../docs/report-compatibility.md#L15-L25)

**Provenance and schema.** The current model has only native and usdchecker provenance, and the report schema constrains those kinds. The current contract preserves enum meanings and distinguishes external records from native findings/coverage. Proposal: decide whether helper coverage belongs in additive optional metadata or a versioned separate record; do not relabel the helper as usdchecker or silently turn external results into native guarantees. Whether a chosen design fits schema major 1 remains open. [Models.swift:72–75](../../../Sources/USDZValidation/Models.swift#L72-L75), [report-v1.schema.json:873–925](../../../Schemas/report-v1.schema.json#L873-L925), [docs/report-compatibility.md:9–17](../../../docs/report-compatibility.md#L9-L17), [docs/report-compatibility.md:25–31](../../../docs/report-compatibility.md#L25-L31)

**Completeness and exits.** Closing supported USDC enumeration would not close expressions/templates, nested packages, unsupported encodings, prerequisite failures or other requested areas. The current resolver also marks policy errors as reference gaps. An exit `2` could become an ordinary complete pass `0` only if all requested areas are truly complete, no finding meets the gate threshold, no higher-priority failure exists, and any requested checker succeeds. `--allow-incomplete` may already accept a gap with `0` while retaining incomplete status. [inspection-boundary.md:9–25](../../../docs/inspection-boundary.md#L9-L25), [ReferenceResolver.swift:143–159](../../../Sources/USDZValidation/Rules/ReferenceResolver.swift#L143-L159), [Models.swift:142–146](../../../Sources/USDZValidation/Models.swift#L142-L146), [GatePolicy.swift:22–48](../../../Sources/USDZValidation/GatePolicy.swift#L22-L48)

**Privacy, safety, and reversibility.** Proposed backends should preserve safe namespace prerequisites, default redaction, deterministic results and explicit unsupported/failure states. Changes to trust boundary, supported formats, resource envelopes, profile meanings or machine contracts need their own decision. Keeping a backend opt-in and retaining the current incomplete result when unavailable would make rollback simpler; a required embedded/native backend creates a larger maintenance commitment. These are design inferences anchored in the existing contracts, not an approved migration. [SECURITY.md:3–13](../../../SECURITY.md#L3-L13), [docs/report-compatibility.md:11–25](../../../docs/report-compatibility.md#L11-L25)

## Evidence needed before a decision

Proposed evaluation, not an implementation plan:

- Define the supported authored-value contract and desired trust mode. Require enumeration from every eligible recognized layer, including mixed USDA/USDC packages, unreferenced layers, inactive authoring, duplicate occurrences and original author directories. Existing lexical tests give parity cases, not a binary oracle. [ReferenceResolverTests.swift:176–191](../../../Tests/USDZValidationTests/ReferenceResolverTests.swift#L176-L191), [NativeEngineTests.swift:243–268](../../../Tests/USDZValidationTests/NativeEngineTests.swift#L243-L268)
- Obtain redistributable real crates with recorded generator/version/arguments/license and known authored references; inventory actual crate versions and relevant feature forms. Current synthetic magic tests prove recognition/gap behavior only. The recorded Apple samples have unverified redistribution rights and are not normal-suite prerequisites. [USDLayerTests.swift:8–36](../../../Tests/USDZValidationTests/USDLayerTests.swift#L8-L36), [docs/fixtures.md:3–15](../../../docs/fixtures.md#L3-L15)
- Establish an independently checked enumeration oracle, including no-reference crates, unsupported features/versions, malformed supported structures, nested identifiers and cap exhaustion. Compare semantics and occurrence attribution, not only checker exit or converted text bytes. No such candidate/oracle comparison was performed here.
- Verify exact OpenUSD/tool behavior and access containment locally before treating any helper, conversion or embedding route as safe. Test invalid output, failures, timeouts, overflow, input changes, host-path attempts, environment/plugin variation and all-layer coverage. The existing adapter tests demonstrate the current fixed invocation, not a new backend. [USDCheckerAdapterTests.swift:110–148](../../../Tests/USDZValidationTests/USDCheckerAdapterTests.swift#L110-L148), [SECURITY.md:11](../../../SECURITY.md#L11)
- Measure candidate peak RSS, time, decoded/output expansion, work caps and repeated-run determinism on a defined host/corpus; cover real maximum-envelope inputs. Current native limits and published targets cannot be transferred to an unmeasured backend. [inspection-boundary.md:33–58](../../../docs/inspection-boundary.md#L33-L58)
- Validate JSON/SARIF/privacy/identity and gate expectations for complete, partial, unsupported, malformed, unavailable and failed backend states. Preserve existing text and checker behavior unless an explicit compatibility decision changes it. Existing golden tests include incomplete and external states, but this run did not execute them. [GoldenCompatibilityTests.swift:15–60](../../../Tests/USDZValidationTests/GoldenCompatibilityTests.swift#L15-L60), [docs/report-compatibility.md:7–31](../../../docs/report-compatibility.md#L7-L31)

## Conditional recommendation

If the priority is **a near-term opt-in aid for trusted local assets**, investigate B1 first, with a strict authored-layer protocol and separately truthful provenance/coverage. Use B2 as a diagnostic or fallback candidate only after proving all-layer and representation parity; current `usdcat` availability is insufficient. This preference is an inference about controllable integration scope, not validated API capability, delivery time or security.

If the priority is **native coverage while preserving the present package-only hostile-input boundary**, investigate D's feasibility against a narrowly stated supported subset before committing to it. Do not replace its proof burden with byte-string scanning. C warrants consideration if a maintained OpenUSD runtime and broader in-process dependency are acceptable product choices; current evidence does not justify selecting it.

If neither trust-mode expansion nor format-parser ownership is acceptable, retain A and the explicit gap. There is no evidence-backed universal winner: prioritizing installation convenience, hostile-input containment, authored parity or long-term format maintenance changes the choice. An unconditional selection should wait for priority clarification and the missing API/format/corpus/resource evidence above.
